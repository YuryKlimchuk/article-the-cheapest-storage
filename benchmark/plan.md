# План испытаний — сравнение хранилищ для аудит-логов

> Цель: выбрать самый экономичный по диску движок для хранения аудит-событий
> (действия пользователей в системе). Результаты пойдут в статью на Medium.

## 1. Цель испытаний

Измерить и сравнить, сколько места на диске занимает один и тот же набор
аудит-событий в разных хранилищах, на разных объёмах данных, и определить
самый дешёвый по диску вариант.

## 2. Варианты для сравнения (кандидаты)

| # | Движок | Тип | Комментарий |
|---|--------|-----|-------------|
| 1 | PostgreSQL | Реляционная СУБД | Базовый вариант, heap + TOAST |
| 2 | TimescaleDB | Time-series (расширение PostgreSQL) | Колоночная компрессия |
| 3 | MongoDB | Документная NoSQL | BSON, WiredTiger (snappy/zstd) |
| 4 | ClickHouse | Колоночная аналитическая СУБД | Сильное сжатие, codecs |
| 5 | MinIO | Объектное хранилище (S3-совместимое) | Файлы объектов, сжатие |

## 3. Объёмы данных

Один и тот же датасет, замер на каждом из размеров:

- 100 000 записей
- 1 000 000 записей
- 3 000 000 записей
- 10 000 000 записей
- 50 000 000 записей
- 100 000 000 записей

## 4. Метрика сравнения

Основная метрика — размер на диске в байтах для каждой пары
(движок × объём данных).

Дополнительно фиксировать (где применимо):
- размер данных отдельно от индексов;
- размер с учётом WAL/журналов;
- итоговый размер после сжатия/компакции.

Обязательный индекс для паттерна доступа — составной `(userId, timestamp)` —
учитывается в замере (его объём входит в результат).

## 5. Единый датасет

Для сопоставимости все движки получают один и тот же сгенерированный набор
аудит-событий. Логическая модель одинаковая для всех движков; физически каждый
движок хранит её в своих нативных типах.

### 5.1. Схема события

| Поле | Логический тип | Пример | Примечание |
|------|----------------|--------|------------|
| `id` | UUID | `3f2a7b9c-…` | уникальный id записи |
| `timestamp` | datetime с tz, точность мс | `2024-01-15T10:30:00.123Z` | время события |
| `userId` | long (int64) | `4201928374` | кто совершил действие |
| `eventType` | enum, 50 значений | `TYPE_1` … `TYPE_50` | тип события |
| `metadata` | JSON-объект | см. 5.3 | данные, зависящие от типа |

### 5.2. eventType

Фиксированный enum из 50 значений: `TYPE_1` … `TYPE_50`.

### 5.3. metadata — 10 вариаций

Содержимое `metadata` зависит от `eventType`. Всего 10 вариаций (V1–V10);
каждому `TYPE_N` соответствует одна из них (см. 5.4).

| Вар. | Название | Поля metadata | Пример |
|------|----------|---------------|--------|
| V1 | auth | `ip` (str), `userAgent` (str), `device` (str), `success` (bool) | `{"ip":"203.0.113.5","userAgent":"Mozilla/5.0…","device":"desktop","success":true}` |
| V2 | entity_action | `entityType` (str), `entityId` (str) | `{"entityType":"order","entityId":"a1b2c3"}` |
| V3 | entity_update | `entityType` (str), `entityId` (str), `changedFields` (str[]) | `{"entityType":"order","entityId":"a1b2c3","changedFields":["status","amount"]}` |
| V4 | search | `query` (str), `resultCount` (int) | `{"query":"laptop","resultCount":128}` |
| V5 | export | `format` (str), `recordCount` (int), `sizeBytes` (long) | `{"format":"csv","recordCount":1000,"sizeBytes":204800}` |
| V6 | payment | `amount` (decimal), `currency` (str), `paymentMethod` (str), `status` (str) | `{"amount":123.45,"currency":"USD","paymentMethod":"card","status":"success"}` |
| V7 | location | `lat` (double), `lon` (double), `accuracy` (int), `country` (str) | `{"lat":55.7558,"lon":37.6173,"accuracy":10,"country":"RU"}` |
| V8 | notification | `channel` (str), `recipient` (str), `subject` (str), `status` (str) | `{"channel":"email","recipient":"u@example.com","subject":"Alert","status":"sent"}` |
| V9 | permission | `resource` (str), `oldRole` (str), `newRole` (str), `grantedBy` (str) | `{"resource":"repo","oldRole":"reader","newRole":"writer","grantedBy":"admin"}` |
| V10 | error | `errorCode` (str), `message` (str), `severity` (str) | `{"errorCode":"E500","message":"timeout","severity":"error"}` |

### 5.4. Маппинг TYPE → вариация metadata

| eventType | Вариация |
|-----------|----------|
| TYPE_1 … TYPE_5 | V1 (auth) |
| TYPE_6 … TYPE_10 | V2 (entity_action) |
| TYPE_11 … TYPE_15 | V3 (entity_update) |
| TYPE_16 … TYPE_20 | V4 (search) |
| TYPE_21 … TYPE_25 | V5 (export) |
| TYPE_26 … TYPE_30 | V6 (payment) |
| TYPE_31 … TYPE_35 | V7 (location) |
| TYPE_36 … TYPE_40 | V8 (notification) |
| TYPE_41 … TYPE_45 | V9 (permission) |
| TYPE_46 … TYPE_50 | V10 (error) |

## 6. Паттерн доступа (запросы)

Основной рабочий запрос — хронология событий одного пользователя за период
времени, по умолчанию за последний месяц:

- `userId` = конкретный пользователь;
- `timestamp` в диапазоне `[now − 1 месяц, now]`;
- события отсортированы по `timestamp` (хронология).

Для этого каждому движку нужен составной индекс `(userId, timestamp)`. Индекс
участвует в замере размера на диске.

## 7. Структура испытаний (фазы)

Испытания делятся на два этапа, чтобы не размывать сравнение.

### Фаза 1 — сравнение движков (основная)

Сравниваем 5 движков в максимально одинаковых и «честных» условиях:

- один и тот же датасет;
- нативные типы и разумные дефолты каждого движка;
- обязательный индекс `(userId, timestamp)`;
- **без** маппинга/сокращения имён полей и без специальных трюков.

Результат: таблица «движок × объём → размер на диске», выбираем лидеров.

### Фаза 2 — оптимизация представления (на лидерах)

На лучших вариантах из фазы 1 пробуем играть с кодированием/маппингом:

- `json` vs `jsonb` (PostgreSQL);
- обычный JSON vs `remapped json` (короткие ключи `f1`, `f2`) vs Avro;
- применимость зависит от того, кто окажется в лидерах.

Результат: сколько ещё можно выиграть на «трюках» поверх выбранного движка.

Детали фазы 2 уточняются после результатов фазы 1.

## 8. Методика (кратко)

1. Стенд на Docker Compose: каждый движок в отдельном контейнере.
2. Генерация единого датасета нужного размера.
3. Загрузка одного и того же датасета в каждый движок.
4. Замер занимаемого места на диске (volume / `docker system df` / `du`).
5. Фиксация версий движков и их конфигурации.

## 9. Допущения и ограничения

- Одинаковое железо и окружение для всех движков.
- Честная конфигурация каждого движка (включить разумное сжатие, где доступно).
- Замер только «полезного» объёма данных, без учёта образов контейнеров.
